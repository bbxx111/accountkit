# v0.7.0 发布说明

状态：已发布（2026-10-28）。tag `v0.7.0`（annotated，对象 `8648467a9a375aad130806c3708fe102112f091e`）固定提交 `6f3b072a8372b83be75b508d1ea521f368c80723`；[最终候选 CI](https://github.com/bbxx111/accountkit/actions/runs/40725361916) 的生成、完整库/服务、race 与真实恢复步骤全部通过，[GitHub Release](https://github.com/bbxx111/accountkit/releases/tag/v0.7.0) 已发布，两个独立宿主已从远端无 replace 消费。证据见[发布验收](../../openspec/changes/archive/2026-10-29-prepare-v0-7-0-release/verification.md)。

本版本在 v0.6.0 之上把消费者 access 改为 ES256 并提供 JWKS 与严格内省，为 accountsvc 增加阿里云短信、已清理用户拉取清单、统一的 `ACCOUNTSVC_` 配置前缀、服务调用 Bearer 认证，以及内置布局加多语言清单的验证码邮件。模块仍为 `github.com/bbxx111/accountkit`，库可独立嵌入，accountsvc 为可选服务。本版本包含破坏性 Go/HTTP/配置变化和当前初始结构变化，升级前请完整阅读“升级与兼容”。

## 消费者 access 改用 ES256 与分级校验

- 消费者 access token 由 HS256 改为 ES256（P-256），header 带 `typ: at+jwt`（RFC 9068），`kid` 仍为十进制版本号，claims 不变。库自身验签拒绝 HS256、`none` 与缺少或错误的 `typ`。
- `accountkit.Config.JWTKeys` 改为 `map[uint16]*ecdsa.PrivateKey`（只接受 P-256），`tokens.Options.Keys` 同理，`tokens.MinKeyLen` 移除；新增 `tokens.ParseKeyList`、`tokens.ParsePrivateKey`、`tokens.CheckKeys`、常量 `tokens.Algorithm`/`tokens.TokenType` 与 `(*tokens.Signer).JWKS`。环境变量 `JWT_KEYS` 仍为 `版本:base64` 列表，值改为 PKCS#8 DER 的 base64；旧 HMAC 值被拒绝并指出变量名，不回显密钥。
- 新增 `Auth.JWKSHandler()` 输出全部已配置版本的验签公钥；accountsvc 在单监听器上挂载 `GET /.well-known/jwks.json`（无认证，可公共缓存 5 分钟）。
- 新增 `user.Service.AuthenticateStrict`、`Auth.RequireScopeStrict` 与 `httpapi/authn.RequireScopeStrict`（接口 `authn.StrictAuthenticator`）：401/403 行为与 `RequireScope` 一致，但吊销以已提交的数据库会话为准、不读 Redis，数据库不可用返回 503；外层已注入 Principal 时仍重新认证。严格认证的指标沿用 authenticate 操作，不新增标签。`Authenticate`/`RequireScope` 的 JWT 加 Redis 吊销与 fail-open 行为不变。
- `POST /v1/introspect` 在 JWT 校验通过后查询数据库会话，会话存在、属于 `sub` 且未吊销才返回 `active:true`；不再读取 Redis 吊销集，数据库不可用返回 503 `temporarily_unavailable`。刷新期限已到但未吊销的会话仍为 active。
- 接入方式改为分级：普通接口用 JWKS 本地验签（接受最多一个 access 有效期加时钟偏差的吊销延迟），关键接口每次调用内省、不缓存结果。`examples/remoteauth` 新增本地 JWKS 验签示例并保留内省客户端；`docs/accountsvc.md` 新增业务服务错误与配置契约（401 `TOKEN_MISSING`/`TOKEN_INVALID`、403 `INSUFFICIENT_SCOPE`、400 `REAUTHENTICATION_REQUIRED`、503 `DEPENDENCY_UNAVAILABLE` 加 `Retry-After: 1`，固定 30 秒时钟偏差），示例的 503 响应与库中间件逐字节一致并由测试保证。

## accountsvc 阿里云短信

- 新增可选包 `user/sender/aliyun`（`Config`、`Sender`、`New`、`ValidateEndpoint`、`DefaultEndpoint`），实现 `sender.SMSCodeSender`：以标准库完成阿里云 SendSms 的 RPC 签名调用，不引入阿里云 SDK；嵌入式宿主也可直接使用。
- accountsvc 新增 `ACCOUNTSVC_SMS_PROVIDER=aliyun` 与 `ACCOUNTSVC_SMS_ALIYUN_ACCESS_KEY_ID` / `_ACCESS_KEY_SECRET` / `_SIGN_NAME` / `_TEMPLATE_SIGN_IN` / `_TEMPLATE_BIND` / `_TEMPLATE_REAUTH` / `_TEMPLATE_SIGN_IN_COMPLETE`，可选 `_ENDPOINT`（只接受 HTTPS，非 production 模式仅额外允许回环地址的 HTTP）。配置了服务商才允许显式启用 PHONE；缺失或非法时 serve 启动失败并指出变量名、不回显值，migrate 不解析。省略身份策略时短信仍保持禁用，不因配置了服务商而自动启用 PHONE。
- 首版只发送中国大陆手机号。发送器可选实现 `SupportsTarget(e164 string) bool`，声明不支持的号码在占用轮次、冷却与额度之前返回 400 `FAILED_PRECONDITION` / `TARGET_NOT_SUPPORTED`（Go 为 `sender.ErrTargetNotSupported`），审计 `CODE_SEND_REJECTED` 原因 `TARGET_NOT_SUPPORTED`；四个发码操作的 OpenAPI 描述同步补充。未实现该方法的宿主发送器不受影响。
- 只有服务商返回 `Code=OK` 才算成功；频控、其他业务错误、网络错误与超时（默认 10 秒）一律按发送失败返回 503，已占额度与冷却不退还，不自动重发，不映射为 429。失败日志记录阶段、HTTP 状态、服务商错误码与 RequestId，不含手机号、验证码、Secret 或服务商消息原文。

## 已清理用户拉取清单

- 账号清理（purge）事务内写入一条已清理记录，与匿名化同提交、同回滚；写入在表锁下串行，`seq` 顺序与提交顺序一致，拉取方不会漏读。新增 `user.PurgedUser`、`user.Service.ListPurgedUsers`（按游标分页，每页至多 `user.MaxPurgedUserPage` 即 1000 条）、`CleanupPurgedUsers` 与 `user.ErrPurgedUserCursorAhead`（满足 `errors.Is(err, user.ErrInvalidArgument)`）；`Config.PurgedUserRetention`（`user.Deps.PurgedUserRetention` 同理）/ `PURGED_USER_RETENTION` 默认 0 表示长期保留，设置时不得短于 720h（`user.MinPurgedUserRetention`），由新增维护任务 `cleanup_purged_users` 删除超期记录。`user.PurgeCoveredTables` 新增 `purged_user` 豁免项。
- accountsvc 新增内部路由 `GET /v1/purgedUsers?page_token=&page_size=`，响应始终带当前位置的 `next_page_token`，空列表表示已追平；`Cache-Control: no-store`，数据库不可用返回 503 `DEPENDENCY_UNAVAILABLE`。鉴权使用独立的 `ACCOUNTSVC_PURGE_FEED_BASIC_CLIENTS`（HTTP Basic，不复用内省凭据）或下文的服务 Bearer 令牌；两种方式都未配置时返回 503 `PURGE_FEED_NOT_CONFIGURED`。网关须与内省一样不对公网开放该路由。
- 业务服务保存游标、按 user_id 幂等清理，并在保留期内完成拉取（建议每 5 分钟一次，落后超过 24 小时告警）。数据库从备份恢复后序号可能回退到业务方已保存的游标之下，此时接口返回 400 `INVALID_PAGE_TOKEN`，业务方清空游标从头重拉。`USER_PURGED` 审计仍只是尽力通知，不是清理完成证据。

## accountsvc 配置前缀统一

- accountsvc 的库配置改为以 `ACCOUNTSVC_` 读取，与服务配置共用一个前缀：每个 `ACCOUNTKIT_` 变量改为 `ACCOUNTSVC_` 加相同后缀，例如 `ACCOUNTSVC_JWT_KEYS`、`ACCOUNTSVC_ENABLED_IDENTITY_KINDS`、`ACCOUNTSVC_ALIPAY_<APPID>_PRIVATE_KEY`；原有 `ACCOUNTSVC_` 服务配置名不变，不读取旧名。
- serve 与 migrate 发现任何非空 `ACCOUNTKIT_` 变量时启动失败并列出旧名与对应新名（不回显值），避免可选配置改名后被静默忽略。测试基础设施变量 `ACCOUNTKIT_RECOVERY_*` 只供恢复演练脚本使用，不得出现在 accountsvc 进程环境中，否则同样被拒绝。
- 直接嵌入库的宿主不受影响：`ConfigFromEnv(prefix)` 仍由宿主自选前缀，`examples/embedded` 与 README 继续以 `ACCOUNTKIT_` 为示例前缀。

## 服务调用 Bearer 认证

- `POST /v1/introspect` 与 `GET /v1/purgedUsers` 在 HTTP Basic 之外可接受外部 OIDC 提供方签发的客户端凭据（RFC 6749 §4.4）RS256 访问令牌；两种方式可同时启用。新增 `ACCOUNTSVC_SERVICE_ISSUER`、`ACCOUNTSVC_SERVICE_AUDIENCE`、`ACCOUNTSVC_INTROSPECTION_BEARER_CLIENTS`、`ACCOUNTSVC_PURGE_FEED_BEARER_CLIENTS`；Basic 凭据变量改名为 `ACCOUNTSVC_INTROSPECTION_BASIC_CLIENTS` 与 `ACCOUNTSVC_PURGE_FEED_BASIC_CLIENTS`，格式不变。
- 令牌须 RS256 且头部带 `kid`、不带 `jku`/`x5u`，`iss`/`aud` 匹配服务 issuer 与 audience，`exp − iat` 不超过 1 小时（时钟偏差 30 秒），按 `azp` 匹配每个接口独立的允许列表；两个列表不得相交，不读取角色或 scope。serve 启动时校验隔离规则：服务 issuer 不得等于消费者 issuer，服务 audience 不得等于消费者、管理员 audience、任一第三方应用/客户端 ID 或任一允许的 `azp`；只配置 issuer/audience 或只配置客户端列表都启动失败。
- 内省的调用认证改为与拉取一样可选：两种方式都未配置时服务照常启动，`/v1/introspect` 返回 503 `introspection_not_configured`，production 同样适用。serve 在监听就绪后为每个未配置的可选接口记一条 WARN（内省、已清理用户拉取、管理员 API、用户资料属性），只写变量名；邮件模板未配置与服务令牌签发方启动时不可用另有各自的 WARN。
- 新错误：内省 401 `invalid_token`、403 `insufficient_scope`；拉取 401 `TOKEN_INVALID`、403 `CLIENT_NOT_AUTHORIZED`；签发方不可用分别为 503 `temporarily_unavailable`、503 `DEPENDENCY_UNAVAILABLE`（`Retry-After: 1`），不当作 401。启用两种方式时 401 返回两行 `WWW-Authenticate`，仅当请求确实携带 Bearer 时附 `error="invalid_token"`。IdP 不可用不阻止服务启动。
- 管理员认证的 OIDC discovery、JWKS 缓存与 JWT 解析抽为内部公共层，管理员认证行为不变。

## 邮件模板清单与多语言

- accountsvc 新增可选 `ACCOUNTSVC_SMTP_TEMPLATES_FILE`：一份 JSON 清单（`version: 1`、`default_language`、1 至 8 种 BCP 47 语言），每种语言提供可选 `brand`、可选 HTTPS `logo_url`、四种用途共用的 `common` 文字与 SIGN_IN / BIND / REAUTH / SIGN_IN_COMPLETE 各自的 `subject`、`heading`、`intro`。版式由嵌入的 HTML 与纯文本布局提供，邮件为 `multipart/alternative`；文字中只允许 `{{brand}}` 与 `{{ttl_minutes}}` 占位符，验证码由布局放置，插入 HTML 时整体转义。
- serve 按发码请求的 `Accept-Language` 选择语言（zh-TW/HK/MO → zh-Hant，zh-CN/SG/zh → zh-Hans，en-* → en），匹配不上、缺失或非法时使用默认语言；网关须透传该请求头，客户端应把界面语言放进去。
- 未设置清单时使用嵌入的无品牌默认清单（简体、繁体、英文，无 Logo、无 `©` 行）并在启动时记录 WARN；配置了清单记录 INFO（版本、清单 SHA-256 前 12 位、语言列表）。日志不含路径、品牌、文字或验证码。校验在 EMAIL 启用时于监听前完成，失败即退出，错误只给变量名、字段位置和固定分类。
- 新增离线子命令 `accountsvc email-templates check <清单> [-out <目录>]`：用与 serve 相同的规则校验，并把每种语言、每种用途渲染为 `.html`/`.txt` 预览与标题汇总。样例见 `deploy/accountsvc/email-templates.example.json`，由测试保证可通过校验。
- 库的 `smtp.LegacyChineseRenderer` 由空结构体改为含可选 `Brand` 字段的结构体（`LegacyChineseRenderer{}` 与零值文案不变，新增 `smtp.ValidateBrand`、`smtp.MaxBrandLength`）；`smtp.New` 默认值与公开 Go API 不变。accountsvc 不再使用该渲染器，v0.6.0 之后曾加入的 `ACCOUNTSVC_SMTP_BRAND` 在发布前撤回，品牌只写在清单里。

## 升级与兼容

本版本以新空 schema 安装为目标，不提供旧库、旧令牌或旧配置的迁移工具。完整对照见[兼容说明](../compatibility.md)中标注随 v0.7.0 发布的前五节。

- **数据库**：当前 0001 按 `add-purged-user-feed` 的明确授权在末尾新增 `purged_user` 表（`user_id` 主键与格式 CHECK、`seq` identity 唯一约束 `uk_purged_user_seq`、`purge_time`）及 `idx_purged_user_purge_time`，down 最先删除该表；无 0002，新安装仍为 version=1/dirty=false。当前 `0001_init.up.sql` SHA256 为 `ef2d1f229fa15b660cc7ecb4f417615b76866c19494641c96faf25bab24188b6`，v0.6.0 发布的 `4c6b565e…` 已作为独立 pin 固定，历史检查分别核验。v0.6.0 及更早结构缺少该表时无写拒绝（`migrations.ErrIncompatibleBaseline`，dirty 优先），保留 catalog、数据与 version/dirty；须使用经人工核验的新空资源，不补表、不 Force、改版本或清库。见[迁移手册](../migrations.md#当前初始基线)。
- **令牌与密钥**：升级后旧 HS256 access 全部失效，客户端收到 401 后用 refresh token 刷新一次即可；refresh token 是数据库中的不透明凭据，不受影响。部署须先生成 P-256 私钥替换 `JWT_KEYS`：

  ```bash
  openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 | openssl pkcs8 -topk8 -nocrypt -outform DER | base64 -w0
  ```

- **内省语义**：依赖“Redis 故障时内省仍放行”的调用方须按依赖不可用处理 503；吊销提交后内省立即返回 `active:false`。业务服务按分级校验接入。
- **accountsvc 配置**：一次完成三项改名：所有 `ACCOUNTKIT_*` 改为 `ACCOUNTSVC_*`；`ACCOUNTSVC_INTROSPECTION_CLIENTS` 改为 `ACCOUNTSVC_INTROSPECTION_BASIC_CLIENTS`；`ACCOUNTSVC_JWT_KEYS` 的值改为 ES256 私钥。残留的任何 `ACCOUNTKIT_` 变量（包括测试用的 `ACCOUNTKIT_RECOVERY_*`）都会使 serve 与 migrate 启动失败并列出旧名。未配置任何内省调用认证的部署不再启动失败，而是在 `/v1/introspect` 返回 503 并记录 WARN，依赖内省的业务服务须确认部署已配置调用方。
- **服务邮件**：accountsvc 未配置清单时改为嵌入的无品牌默认清单（HTML 加纯文本、新版式、三种语言），原纯文本中文邮件的逐字内容不再由服务输出；需要品牌或自定义文案的部署配置 `ACCOUNTSVC_SMTP_TEMPLATES_FILE`。`ACCOUNTSVC_SMTP_BRAND` 从未发布，无迁移。
- **Go 宿主**：`Config.JWTKeys` 与 `tokens.Options.Keys` 的类型变化在编译期即可发现，测试可用 `ecdsa.GenerateKey(elliptic.P256(), rand.Reader)` 构造密钥；`smtp.LegacyChineseRenderer{}` 继续可用，需要品牌时使用 `LegacyChineseRenderer{Brand: …}`，`smtp.NewWithRenderer` 对品牌不合法的该渲染器在构造时返回错误；宿主自己的 user_id 覆盖性测试若枚举库内表，需知道 `purged_user` 只含 user_id 与时间；`RunMaintenanceOnce` 的任务顺序新增 `cleanup_purged_users`。嵌入式宿主无需改动路由，可按需把关键路由换成 `RequireScopeStrict`。
- **回退**：回退到 v0.6.0 须同时恢复旧的 HS256 配置、旧前缀与旧内省变量名，此时 ES256 access 失效，客户端刷新即可。旧二进制的预检不检查 `purged_user`，会接受新 version 1 结构，但其 purge 不写已清理记录，对应账号将永久缺席拉取清单；部署须人工阻止新旧版本混跑和在新结构上回退到旧二进制，不通过清库或改版本回退。

## 运行与验证

Go 1.26.5、PostgreSQL 17、Redis 7、sqlc 1.31.1；go.mod/go.sum 相对 v0.6.0 无变化，语言匹配使用已有依赖 `golang.org/x/text/language`。两面 OpenAPI 版本为 v0.7.0，操作集合与 v0.6.0 相同，只补充 `TARGET_NOT_SUPPORTED` 的描述；JWKS、内省、已清理用户拉取属于 accountsvc 专属路由，不在库契约内。

交付 Go module 与源码（含可选 accountsvc），不包含服务镜像、二进制或产品部署。当前未附开源 LICENSE，仍面向自有产品。阿里云短信以本地 HTTP 替身验收，未用真实凭据与已审核模板发送；邮件布局以黄金文件与 SMTP fixture 验收，未在真实邮件客户端核对显示效果；服务 Bearer 认证以本地签发方替身验收，未与真实 IdP 联调。这些以及网关、监控与目标环境验收由集成方按[上线清单](../release-checklist.md)完成。
