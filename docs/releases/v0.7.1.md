## 开发模式的明文 HTTP 签发方

- 触发条件：仅 `ACCOUNTSVC_MODE=development`。此时 `ACCOUNTSVC_ADMIN_ISSUER` 与 `ACCOUNTSVC_SERVICE_ISSUER` 额外接受 `http://` 绝对 URL；其余约束不变（无凭据、查询、片段与首尾空白）。不新增开关变量，没有自定义 CA 或跳过证书验证的选项。
- 整条链路一致放开：discovery 文档地址（由 issuer 派生）、discovery 返回的 `jwks_uri` 与令牌 `iss` 精确匹配都按 HTTP issuer 工作；重定向仍一律拒绝。`iss` 与 discovery `issuer` 必须与配置值逐字相同，容器内使用 `http://host.docker.internal:<port>/realms/<realm>` 时须让 IdP（如 Keycloak 的 hostname 设置）在容器内外返回同一字符串。
- 启动日志：serve 在 migrate 之后、管理员 discovery 之前为每个 HTTP issuer 各记一条 WARN，只写变量名不写值：`accountsvc: administrator issuer uses plain HTTP; allowed only in development mode`（`settings=ACCOUNTSVC_ADMIN_ISSUER`）与 `accountsvc: service token issuer uses plain HTTP; allowed only in development mode`（`settings=ACCOUNTSVC_SERVICE_ISSUER`）。migrate 不记录。
- production（默认）行为不变：HTTP issuer 仍在监听前拒绝，错误信息与变量名与 v0.7.0 相同；production 下 discovery 返回 HTTP `jwks_uri` 仍判定签发方不可用（管理员 issuer 使启动失败，服务签发方使 Bearer 调用返回 503 直到恢复）。
- 内部实现：`internal/accountsvc/oidcjwt.Options.AllowHTTP`、`adminauth.Config.AllowHTTP`、`accountsvc.ServiceConfig.AllowHTTP`，均为内部包，不属于库的公开 API。
- 文档：[accountsvc 配置](../accountsvc.md#配置)的 `MODE`、`SERVICE_ISSUER`、`ADMIN_ISSUER` 条目与新小节[本地开发的明文 HTTP 签发方](../accountsvc.md#本地开发的明文-http-签发方)；`deploy/accountsvc/.env.example` 注释。

## 升级与兼容

- 从 v0.7.0 升级无需任何改动：配置、令牌、数据库与客户端行为完全兼容。当前 `0001_init.up.sql` SHA256 仍为 `ef2d1f229fa15b660cc7ecb4f417615b76866c19494641c96faf25bab24188b6`，与 v0.7.0 逐字节相同，无 0002，新安装仍为 version=1/dirty=false；go.mod/go.sum 无变化。
- 本地 compose（`deploy/accountsvc/compose.yaml` 已设 `ACCOUNTSVC_MODE: development`）可直接通过 `ACCOUNTSVC_SERVICE_ISSUER` 配置 HTTP 服务签发方；管理员认证变量未纳入该模板，需自行加入环境。production 部署若误设 HTTP issuer 仍会启动失败。
- 回退到 v0.7.0：仅当 development 配置了 HTTP issuer 时需要改回 HTTPS（或关闭对应功能），其他无影响。
- v0.7.0 的全部升级边界（ES256、内省语义、`ACCOUNTSVC_` 前缀、`purged_user`、服务邮件清单）继续适用于从 v0.6.0 及更早版本升级，见 [v0.7.0 发布说明](v0.7.0.md#升级与兼容)。
