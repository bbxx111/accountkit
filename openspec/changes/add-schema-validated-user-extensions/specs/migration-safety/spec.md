# Spec Delta

## MODIFIED Requirements

### Requirement: 升级保留已有数据

发布 SHALL 包含真实 PostgreSQL 上受支持非空数据库到正式后续版本的验证。本次 SHALL 覆盖固定 v0.4.0 version 1 到扩展资料 version 2，保留账号、身份、会话、审计、流程、来源及客户端描述；重复 Up SHALL 无变化。仅用于验证失败和下一版本的脚本 SHALL 继续放在测试目录，不能混入生产源。旧基线退出自动升级支持的说明及历史数据格式验证 SHALL 保留。

#### Scenario: 非空数据库升级
- **WHEN** v0.4.0 基线包含用户、身份、会话、审计、流程及完整会话上下文，并升级到本次正式 version 2
- **THEN** 版本前进且原有记录、约束及认证能力保持；扩展获得空初值，再次升级不重复执行

#### Scenario: 测试版本继续独立
- **WHEN** 在本次生产 version 2 上执行成功、失败及 dirty 阻断测试
- **THEN** 测试源使用独立下一版本，生产嵌入目录不包含测试 probe 或失败 SQL

#### Scenario: 升级恢复证据
- **WHEN** 对本次版本进行完整发布验收
- **THEN** 在独立空恢复库验证含扩展资料和版本元数据的备份恢复，保留源库不变证据；未运行或跳过真实演练不能报告完成

### Requirement: 已发布迁移不可改写

发布 SHALL 核验完整历史与全部可达正式标签，拒绝已发布迁移修改、删除、重编号，后续变更递增。v0.4.0 的 `0001` 已发布，其标签固定为 `62f0799b6c6ef1603b33f81834d39033dd0d0c4d`，本次只新增生产 `0002`。此前初始整合、审计/索引维护和会话简化的授权仅适用于各自发布前变更，不再授权修改当前 `0001`。冻结源、manifest、v0.1/v0.2/v0.3.0/v0.4.0 精确标签及原始 SQL SHALL 保持，不移动标签、覆盖旧哈希、Force 或增加忽略历史检查的开关。

#### Scenario: 修改历史 SQL
- **WHEN** 对应基线中的已发布 SQL 变化或消失
- **THEN** 发布检查失败指出文件，不能覆盖冻结源或新增 tag 绕过

#### Scenario: 固定历史发布
- **WHEN** 检查固定 v0.1.0、v0.2.0、v0.3.0 和 v0.4.0
- **THEN** 核对精确提交和各代原始 SQL，移动同名 tag 不能获得豁免

#### Scenario: 用户授权调整原始定义
- **WHEN** 追溯此前通用审计直接调整未发布 `0001`
- **THEN** 保留当时限定授权及历史记录，本次扩展通过增量迁移实现，不扩大历史授权

#### Scenario: 整合后发布
- **WHEN** 新正式 tag 或合并分支新增迁移
- **THEN** 校验当前初始及各代全部已发布增量，HEAD 标签不能掩盖篡改，新增版本严格递增

#### Scenario: 用户授权统一独立索引名称且不新增迁移
- **WHEN** 追溯此前未发布 `0001` 索引改名
- **THEN** 保留 22 个普通 idx_ 与 4 个独立唯一 uk_ 的当次限定授权及原定义证据，不用于扩大本次范围或自动修改已有索引

#### Scenario: 本轮授权简化会话初始结构
- **WHEN** 追溯 v0.4.0 发布前移除 known 和双快照的简化工作
- **THEN** 保留当时 version 1、无生产 `0002` 的验收证据；该历史事实不阻止本次正常递增，也不解除旧 v0.3.0 v1、双快照 v1 和已撤回历史 v2 的拒绝保护
