## Context

动机与范围见 [proposal.md](proposal.md)，行为契约见 [轮换规格](specs/code-key-rotation/spec.md)。本变更涉及认证并发和存量 Redis 数据接管，因此需要设计工件。

当前 `user/code.Store` 将 active 目标 HMAC 摘要放入 `code`、`cooldown`、目标 `quota` 键名；IP 日额度不依赖 HMAC。验证码 hash 仅含摘要 `h` 和计数 `n`，没有可比较的签发时间。校验虽已有多版本验证码摘要，但只查 active 的目标键。发码和校验目前各由一次 Lua 完成，必须保留这种原子边界。

`pii.Digester.AllDigests` 可计算全部已配置版本，active 在前；不同版本允许相同密钥材料，输出可能重复。旧实现每次发码只增加 active 目标计数，因此旧目标日额度可通过去重后的物理键求和，不能取最大值，也不能双写计数后直接求和。

现有 [嵌入契约](../../../specs/embedded-auth-package/spec.md) 和 [投递契约](../../../specs/verification-delivery/spec.md) 继续适用。数据库摘要回填在维护任务中按本进程 active 执行，默认每 5 分钟调度；本变更保留该行为。

## Goals / Non-Goals

**Goals:**

- 保持旧键格式及 hash 字段，接管单份旧码时无需扫描、搬迁、续期或新增数据库状态。
- 让不同 active、相同完整密钥集合的进程对同一逻辑验证码和发送限制做出一致判断。
- 将原子性集中在两段 Lua 中；Go 负责键/候选摘要构造、参数传入和明确的结果映射。

**Non-Goals:**

- 不增加每目标分布式锁、稳定索引密钥、版本指针、别名表、全库 SCAN 或存量 Redis 搬迁任务。
- 不改变公共构造函数、根 Config/Deps、发送器契约或 HTTP 协议；不改变数据库维护调度或新增手动回填动作。
- 不支持旧程序同时参与 active 轮换的强连续性，不借此增加 Redis Cluster 跨槽支持。

## Decisions

### 1. 统一构造并去重全部版本的目标键

按 `AllDigests(target)` 生成目标摘要，按摘要值去重且保留 active 的第一个位置；沿用已有实例前缀、渠道、用途和 UTC 日期组合。每次操作将实际访问的键全部显式作为 KEYS 传入 Lua，参数边界明确，不依赖不同进程的 active 排列一致。验证码摘要候选同样按值去重。

新写入仍使用 active 目标键和 active 验证码摘要；读取考虑全部已配置版本。不改变 `pii.Digester` 的公共语义或全局排序。

替代方案：只给 Verify 加旧键回退，无法保证重新发码作废旧记录与发送限额；独立稳定索引密钥需要新增配置及自身轮换设计。本次采用现有键的统一处理。

### 2. 发码在一次脚本内检查、占额和替换

脚本依次执行以下逻辑，沿用错误优先级：

1. 检查全部目标冷却键；若存在有效冷却，取最大剩余 TTL，返回 COOLDOWN。正常路径 RetryAfter 至少 1 秒；不因 active 顺序返回较短冷却。
2. 对全部不同物理目标日额度键求和，达到上限返回 TARGET_LIMIT。
3. 检查唯一的原 IP 日额度键，达到上限返回 IP_LIMIT。
4. 全部检查通过后，仅在 active 键写冷却、增加一次目标额度，并增加一次 IP 额度；新日计数键继续使用既有 UTC 日界线加 1 小时的清理 TTL。
5. 删除所有版本的同用途验证码键，仅在 active 键写入新 `h`、`n=0` 和原 CodeTTL。

拒绝发送不改动任何正常业务状态。旧目标额度保持原键及 TTL，不汇总写回 active 键，否则后续读取会重复累计。不同用途的验证码不被重新发送操作删除，但共用既有目标冷却和额度。

### 3. 校验保持单份签发状态，不延长寿命

在一次脚本内检查去重后的候选验证码键：

- 无存活记录：返回 MISSING，映射既有 ErrExpired。
- 恰好一份记录：在该记录上沿用原逻辑增加 `n`，超过 MaxAttempts 时删除并返回 EXHAUSTED；否则比较全部候选验证码摘要。匹配后删除并返回 OK，未匹配返回 MISMATCH。全程不移动记录、不刷新 TTL、不重建尝试计数。
- 存在多份不同物理记录：不能从旧 hash 或剩余 TTL 可靠推断最新签发顺序，原子删除这些冲突码，返回 MISSING；保持冷却和额度，用户可按原限制重新发码。即使 `h` 相同也不把不同物理记录视作已证明的同一签发。

此冲突分支用于历史上不受支持的 active 混跑留下的状态；遵循部署前提的新实现自身始终只保留一份记录。拒绝按 active 选记录或逐键尝试，因为会使不同进程接受不同签发、扩大尝试预算或使旧码复活。

对脚本执行错误、畸形返回值及未知状态明确返回 ErrUnavailable，不默认放行。此处保证验证码存储的 fail-closed；不承诺 Redis 故障下没有任何已完成写入，也不在投递失败后退额。

### 4. 操作成本与边界

目标键数量与已配置的不同 HMAC 密钥数量线性相关，不进行 Redis 全局遍历。密钥集合和验证码策略是服务实例的部署一致性前提，不新增运行时协调协议或必填配置。

额度按 UTC 日键计算，目标/IP 日限的 RetryAfter 沿用下一个 UTC 零点；保留 1 小时清理宽限但不把它解释为业务限流窗口。校验失败计数沿用现有边界：最多 MaxAttempts 次提交可进入比较，第 MaxAttempts+1 次作废并返回 EXHAUSTED。

### 5. 验证覆盖库与服务接入

- 使用同一 Redis、同一前缀、相同密钥集合而 active 不同的两个 Store，覆盖 PHONE/EMAIL 与三种用途、双向验证、部分错误次数、原 TTL、轮换后重发、额度累计和去重。
- 使用原始旧键/hash 夹具验证升级接管，避免仅测试新实现写入的数据；构造历史冲突双记录验证拒绝策略。
- 并发测试验证跨 active 发码至多一胜、同码消费一胜、发码与校验串行化；使用固定不同码夹具避免随机码恰好相同导致伪失败，不通过修改生产随机源满足测试。
- 在可识别的一次性真实 Redis 上复核脚本、TTL、计数和并发；miniredis 用于快速行为测试，不能代替全部真实 Redis 证据。
- 库领域/HTTP 集成覆盖登录、绑定/换绑及重新认证使用旧码，并验证审计、错误映射、发送失败额度保留和实例隔离；复用已有一次性 PostgreSQL 基础设施。
- accountsvc 使用测试投递设施，在分发完整密钥后以不同 active 重启/并行运行，验证旧码登录及发送限制；不访问实际邮件、短信或产品环境。
- 维护必需测试清单并运行项目要求的检查；验收结果放本 change 的 verification.md，明确真实环境验证仍按用户要求延期。

## Risks / Trade-offs

- [进程密钥集合不一致] → 新进程写入的键可能对旧配置不可见；先完成全量密钥分发，再切换 active，不声明对缺失密钥的连续性。
- [旧程序混跑或历史重复码] → 程序升级与密钥切换分开；重复存活记录拒绝校验并作废，不猜测新旧顺序。
- [历史计数分裂] → 原实现每次只写一个目标计数，求和可以保留实际用量；不复制计数，不取最大值，物理键去重。
- [过早移除旧密钥] → 同时核对数据库引用和 Redis 业务窗口；现有 Migrate 只检查数据库引用，不包装成完整的轮换退役检查。
- [周期性回填在混合 active 期间改变方向] → 按用户决定保留现有机制，在部署说明中明确仅在所有旧进程及在途维护结束后确认回填完成。
- [版本数增加放大脚本开销] → 文档说明只保留仍需读取的版本；不新增任意版本数上限或公开配置兼容变更。

## Migration Plan

1. 保持 active 不变，先将所有进程升级到本实现；新旧程序在相同 active 下沿用相同键格式。
2. 向所有进程分发完整 K1、K2 集合，仍 active=K1；确认版本与验证码策略一致后，滚动切换到 K2。不更换旧版本编号对应的密钥材料，不改变实例前缀。
3. 记录最后一个 K1 active 进程及其在途操作结束的时刻 T0。所有后续写入与维护应使用 K2；等待既有周期性回填完成，查询实际 schema 下未删除身份对 K1 的引用为零。
4. Redis 业务等待截止为 `max(T0 + 旧 CodeTTL, T0 + 旧 CodeCooldown, T0 之后的下一个 UTC 零点)`。配置曾变化时使用仍可能存活记录对应的最大旧期限，并留出部署时钟偏差余量。日额度的额外 1 小时仅用于垃圾回收，不要求为业务退役额外等待该小时。
5. 数据库和 Redis 条件同时满足后，从全部运行配置移除 K1 并部署。为仍需恢复的旧备份受控保留相应历史密钥；退役不等于立即永久销毁。

回退优先保留支持多版本的程序和完整密钥集合，仅将 active 改回 K1，校验与发送限制仍连续；按实际最后旧写入时刻重新计算退役窗口。切回不支持本能力的旧程序不能承诺轮换后的连续性，即使键格式兼容也会忽略其他版本记录；此类回退需要单独制定窗口，不通过清空 Redis 或恢复计数实现。
