## Decisions

### 1. 直接定义最终结构

0001_init.up.sql 中直接 CREATE 五个业务表及全部现有索引/约束；audit_event.flow_id 放在原 occur_time 之后，以保留列顺序并降低 sqlc 生成差异。identity_flow 使用当前字段和类型，枚举无新增 CHECK。down 按依赖顺序覆盖五个表，仅供现有明确危险测试清理；公开 Down 仍无 I/O 拒绝。

删除生产 0002，将测试探针从 0003/0004 恢复为 0002/0003。新库 version=1、dirty=false。未来真实结构变更从 0002 开始递增。

### 2. 独立核验两代迁移基线

source-baseline 的原始 SQL 和 manifest 保持原字节及固定哈希。迁移检查另固定整合后初始 SQL 的哈希。可达历史标签 v0.1.0、v0.2.0 分别固定到 48603d6d349c57910328d393d5e17decec934f11、e19af8542f099f14103627140c0fe23f14c99b7e，仅这两个精确发布使用原基线；标签被移动或其 SQL 异常必须失败。

所有其他可达正式标签使用整合基线，仍合并核验已发布增量，包括合并分支和 HEAD；任何新标签不能恢复旧初始 SQL、删除/修改后续版本或以环境开关绕过。检查仍拒绝浅克隆、版本冲突和非递增新增迁移。固定源快照和新版哈希各司其职，不能靠更新原 manifest 通过检查。

### 3. 旧库明确拒绝

在现有锁范围内、迁移应用前，对已有迁移记录辨认旧版本的结构：旧 version=1 缺少 identity_flow/flow_id，或整合前 version=2 在当前单版本源中均不可直接使用。返回明确迁移基线不兼容错误；不改版本、不重建表、不清 dirty、不删除数据。测试注入下一版本仍可完成新基线 1→2 的正常升级；已经完整安装的新 version=1 重复运行成功。dirty 保持原引擎错误优先级。

### 4. 分离格式兼容与旧结构接管

历史合成数据的 ID、密文、摘要、access 与 refresh 兼容继续验证，但将数据装载到完整的新基线，而不宣称旧 schema 可原地接管。原 TestSourceDatabaseTakeover 一对一更名为反映新基线格式兼容的测试，required-tests 同步；新增旧库拒绝行为门禁，不移除并发、恢复或失败测试。

恢复演练使用新的完整初始版本，仍验证旧密钥、完整完成 pair、PENDING 缺 Redis 证明拒绝、原版本/dirty 和源库保持。真实微信/Apple 联调仍属于前一变更未验证项，不在本次重复要求。

## Risks / Trade-offs

- 旧开发库与新 version=1 数字相同 → 用必要结构辨认并明确拒绝，不允许静默 no-op。
- 初始 SQL 不等价 → 比较整合前两段 SQL 与新初始 SQL 在 PostgreSQL 上的目录/索引/约束及 sqlc 结果；新增列顺序保持。
- 历史检查例外过宽 → 精确历史 tag+commit 白名单和两代固定校验值；用新标签/合并分支/篡改测试证明没有通用旁路。
- 开发者误清库 → 文档仅说明经核验的一次性资源重建，不运行自动清理，不推荐 Force 或更改 schema_migrations。
