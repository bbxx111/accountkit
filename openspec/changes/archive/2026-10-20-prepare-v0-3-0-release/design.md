## Context

上一固定版本为 v0.2.0。本次准备基线为 develop 的 c3bdc8d788ce6a088f3a0b4da866280916c7ae9b；发布说明按最终行为整理，不能把开发过程中的旧 /accounts 路径、已撤回增量迁移或中间审计方案描述为对外发布内容。

## Goals / Non-Goals

目标：准备 v0.3.0 说明、当前代码的验证证据及明确的发布门禁，并按准备完成后用户的继续授权执行正式发布和远端消费确认。非目标：新增功能、替集成方验收真实环境、自动迁移旧数据库、产品部署或自动归档。

## Decisions

- 使用 v0.3.0；用户已确认版本号。保留 v0 阶段明确的破坏性升级说明，不暗示向后兼容。
- 独立记录初始数据库、登录结果、审计模型/游标和可兼容类型别名，分别指向长期兼容文档。
- 从完整 Git 历史复制精确运行时快照到 Linux 验证容器，使用专用 PostgreSQL 17 和 Redis 7。准备阶段文档变化单独检查；真正发布时仍需确定 main 候选及其 CI，不能用开发基线的成功冒充最终发布提交已通过。
- 所有实际结果与未验证项集中在 verification.md；docs 只维护说明和流程入口。本次纯文档维护直接执行，不启动功能开发 apply，也不新增重复的行为测试。
- 产品联调和生产环境验收由集成方负责；微信/Apple 任务 8.5 仍保留未验证。

## Risks / Trade-offs

- 新旧基线 version 均可能为 1，但结构不同。发布说明必须优先指出旧库拒绝、数据迁移另行验证及禁止 Force/清库的边界。
- 完整本地门禁只证明记录的代码与测试快照；最终 main 提交、远端固定版本消费和真实产品环境需要各自证据。
- 发布完成后需补充固定 SHA、CI 和消费记录，更新历史状态说明；当前文档不得预先宣称已发布。
