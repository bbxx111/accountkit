## Context

当前 0001 是 v0.3.0 已发布结构，0002 为尚未发布的会话认证上下文。用户本轮明确选择把后者并入当前初始定义，覆盖仓库默认禁止改写当前 0001 的规则，仅限本次整合。历史版本仍从原 tag 消费。

## Goals / Non-Goals

目标：新安装用完整 0001 达到 version=1，重复 Up 无变化；旧同号结构及撤回 v2 显式拒绝；历史与当前 SQL 分别固定。

非目标：不提供数据转换、Force、清库、版本修正或自动接管，不改认证业务或已发布 tag，不发布新版本。

## Decisions

1. 在 session 的 CREATE TABLE 中定义 authentication_identities_known，并保持其位于原字段末尾，以维持与原 0001+0002 完全相同的列序。原 0002 两张表及两个索引并入 0001，down 配对覆盖七张表；公共 Down 仍无 I/O 拒绝。
2. 当前 v1 预检要求完整上下文结构；旧 v0.3.0 v1 即使非空也只读拒绝。撤回 v2 在生产源中不存在，应拒绝而不降版本；后续测试专用 v2 仍可通过注入源正常验证升级。
3. 历史检查按精确提交及固定哈希分三代：v0.1/v0.2 原冻结源、v0.3.0 原初始结构、当前整合结构。独立核验三个固定历史 ref 的存在和精确提交，再遍历可达正式发布；删除标签或移动到 HEAD 不可达提交也须拒绝。v0.3.0 不能按 tag 名无条件豁免，不得接受错误历史字节或未来版本复用旧初始定义。
4. 保留原本有意义的升级/dirty/锁/隔离/恢复测试。新增真实 PostgreSQL 场景验证旧 v0.3.0 和撤回会话 v2 的无写拒绝；新初始 catalog 与整合前两份 SQL 组合对比，避免拼接改变列序或约束。
5. 原已归档变更记录保持历史语义，本轮结果写入本变更 verification.md；活跃文档改为新基线，v0.3.0 发布说明继续说明该版本实际交付。

## Risks / Trade-offs

旧 v0.3.0 数据库不再有本分支原 0002 的自动升级路径；新部署须人工核验新空资源，有保留数据需求时另行设计迁移。旧 v0.3.0 预检只核验流程/审计，不检查会话上下文，折回 v1 后旧程序可能成功启动，部署方必须显式阻止混跑或未经核验的回退，不能把旧预检作为保护。应用回退须独立验证，DDL 看似相同不代表行为可互换。此授权不允许日常重写初始 SQL。

## Migration Plan

仅修改源码、测试与说明，不运行现有实例的 Up/Down 或清库。验证仅使用本任务创建的一次性 PostgreSQL/Redis。后续发布必须明确此次基线变更并重新执行最终候选门禁。
